# Keepa (`services/keepa.py`)

## What this does

Client for the Keepa API, used two ways across the app: (1) **Product Finder** (`find_asins`) — discovers full brand/manufacturer ASIN catalogs past SP-API's own keyword-search recall ceiling (used by Brand Analytics); (2) **live `/product` data** (`fetch_products`) — Buy Box price/history, FBA fees, ranks, ratings, dimensions (used by the Vendor Offers "Offer Analytics export" and PO Analytics, which reuses that same export machinery).

## Architecture

- `find_asins(brand=None, manufacturer=None, min_rank=None, max_rank=None, min_sold=None, max_sold=None)` — Product Finder query. Caps at **10,000 ASINs per selection**; `page` pagination does NOT go deeper (page 1 returns 0 beyond the cap), so the function **recursively partitions on `trackingSince`** (every tracked product has one) until each partition ≤10k, then merges+dedupes. Token cost = 10 + 1/100 ASINs. `_term_variants()` expands a term into punctuation/suffix variants (trailing period/comma, lp/inc/llc/ltd/co/corp ±period) passed as a Keepa OR list, so a missing period on a legal-entity suffix never silently loses most of a brand's catalog. `min_rank`/`max_rank` and `min_sold`/`max_sold` are applied via `current_SALES_gte/lte` and `monthlySold_gte/lte` directly in the finder query — filtered IN Keepa for no extra token cost.
- `discover_sub_brands(seed, extra_terms)` — samples ~500 products under the seed's manufacturer/brand fields via Keepa `/product` (history/stats=0, ~1 token/ASIN), tallies distinct brand-field values, and only looks up a candidate's exact finder count if it clears a confidence floor (≥3 raw sample hits AND ≥2% of all samples examined) — stops a brand that merely happens to be big elsewhere on Amazon from outranking the genuine seed brand based on a single noisy sample hit.
- `discover_entities(seed)` — for a seed brand string, samples products' `brand`/`manufacturer` fields and returns the real Keepa-registered spellings + exact finder counts — used by Check Brand's resolution chain (`docs/features/toolbox.md`) as a structured-field-exact fallback when a free-text vote resolver is too noisy.
- `fetch_products(asins, on_progress=None, should_cancel=None)` — live `/product` calls, 100-ASIN batches, using the **`buybox=1`** request parameter (not `offers=N`, which ships every offer object per ASIN and can blow past response-size limits — see Changelog 2026-09-03) to get Buy Box price/seller/share plus 30d/90d averages in a small per-ASIN payload. Also passes **`rating=1`** (see Changelog 2026-10-07b) — without it Keepa never populates the RATING/COUNT_REVIEWS stats slots, always returning `-1`, even for products with thousands of real reviews; this was a latent whole-app bug since both PO Analytics and the Offer Analytics export share this function. A Keepa error containing "token" (case-insensitive) is treated as recoverable (retry with backoff) rather than fatal; a batch that still fails after every retry is skipped with a warning (its ASINs get no Keepa data) rather than raising out of the whole export job — a multi-hour export can no longer lose everything to one bad batch near the end. **Cached 2 days** (`keepa_product_cache`, see Changelog 2026-10-19) — an ASIN fetched recently skips the live call entirely.

## Changelog

**2026-10-19b — Found and fixed the REAL cause of recurring 429s on Keepa's own dashboard: a 3x too-low token-cost estimate, plus the explicit 5% reserve margin the user asked for:**
- User: "I am looking at keepas dashboard and I see that we keep hitting 429 error could we make it so that out of 400 tokens (we upgraded just now) we leave like 5% of tokens left."
- **Investigated live before changing anything.** Queried Keepa's own `/token` endpoint directly: `refillRate: 400` (confirms "400" = the account's live per-minute refill rate after the user's upgrade, not a hardcoded number this app should bake in) and `tokensLeft` can sit well above that (the bucket accumulates beyond one refill cycle if unused). Then made a REAL `/product` call with the exact params `_call_product` always sends (`buybox=1, stock=1, fbaFees=1, rating=1, stats=30/90`) against 3 real ASINs and read back `tokensConsumed` directly: **6.0 tokens/ASIN**, confirmed identically on both the stats=30 and the stats=90 call.
- **Found the actual bug**: `_call_product`'s pre-flight `need` estimate was `max(20, len(asins) * 2)` — i.e. 2 tokens/ASIN, a **3x undercount** of the real 6/ASIN cost. For a 100-ASIN batch that's `need=200` against a real cost of `600` — `_wait_tokens` would happily let the call through with, say, 250 tokens left (>= the wrong 200 estimate), the request would then actually consume 600, driving the REAL balance deeply NEGATIVE — which is exactly what trips Keepa's own 429 on every subsequent request until the bucket refills back to positive. This is almost certainly the real, measured root cause of what the user was seeing on Keepa's dashboard, not just "we need a bigger safety margin" — fixed the actual number first (`need = max(20, len(asins) * 6)`).
- **Then added the explicit 5% reserve margin on top**, exactly as asked: `_wait_tokens(sess, need)` now also computes `reserve = int(refillRate * 0.05)` from the SAME live `/token` check already being made (not a hardcoded "400" — this keeps tracking correctly through any future plan upgrade/downgrade) and requires `tokensLeft >= need + reserve` before proceeding, instead of just `tokensLeft >= need`. This benefits all 3 existing `_wait_tokens` call sites (`_call_product`, `seller_asins`, `_call_sellers`) for free.
- **Verified live, precisely**: with a real `tokensLeft=96` and `refillRate=400` (reserve=20), asking `_wait_tokens` for a `need` that would leave only 2 tokens (well inside the 20-token reserve) correctly made it WAIT instead of proceeding; asking for a small, safely-within-margin `need=10` correctly returned immediately (0.37s, no wait).
- Scope: `services/keepa.py` only (`_call_product`'s `need` formula corrected; `_wait_tokens` gained the `reserve`/`_RESERVE_PCT` logic). **Needs a backend restart.**

**2026-10-19 — `fetch_products` now caches live /product results for 2 days:**
- User (mid-conversation, while discussing the Vendor Offers export's Keepa/eligibility phase ordering): "could you please cache eligiblility for 1 week, and keepa data for 2 days." This entry covers the Keepa half; see `docs/infra/sp_api.md` (or `services/restrictions.py`'s own doc comment) for the eligibility half, which lives in a different module.
- **New `keepa_product_cache` table** (`asin TEXT PRIMARY KEY, data_json TEXT, as_of TEXT`) + `_product_cache_get`/`_product_cache_put` (`_PRODUCT_CACHE_TTL_DAYS = 2`), same shape as the existing storage-fee cache pattern (`services/storage_fees.py`). `fetch_products()` now checks the cache FIRST — only ASINs not already cached within 2 days go into the live batch-fetch loop; progress (`on_progress`) immediately reports the cache-hit count as already-done before the live loop even starts, then increments normally through the remaining live batches. Only newly-fetched rows are written back to the cache (a cache hit is never re-written, so its `as_of` timestamp — and thus its real age — is preserved).
- **Honest tradeoff, not hidden**: Buy Box price/rank/etc. can genuinely move within 2 days — a cache hit may show up-to-2-day-old pricing. This is the user's own explicit, deliberate choice (fewer live Keepa calls and tokens spent vs. always-fresh data), not a default anyone should assume elsewhere.
- **Verified live**: cleared the cache for 2 real ASINs, confirmed a cold `fetch_products()` call takes real time and returns real data (e.g. a live title/Buy Box for `B014TDI4GA`); an immediate second call for the same 2 ASINs returned byte-identical results in 0.0s (full cache hit, zero live Keepa calls); a mixed call (2 cached + 1 not) correctly reported progress as `(2, 3)` immediately then `(3, 3)` after the one live fetch, and returned all 3 results correctly.
- Scope: `services/keepa.py` only (`fetch_products` rewritten, `_product_cache_get`/`_product_cache_put`/`_ensure_product_cache_table`/`_PRODUCT_CACHE_TTL_DAYS` added; new `datetime`/`services.database` imports). All 3 existing callers (Vendor Offers export, PO Analytics, Seller Analytics) are unaffected at the call-site level — same function signature, same return shape, caching is entirely internal. **Needs a backend restart.**

**Changes this session (2026-10-07b) — shared `keepa.py` bug: Total Ratings Count was 0 for every row across the whole app:**
- Root cause: `_call_product()` never passed Keepa's `rating=1` request parameter, so the `RATING`/`COUNT_REVIEWS` stats slots were never populated (always `-1`), even for products Keepa's own `hasReviews` flag confirms have thousands of real reviews. Verified live: the exact same ASIN returned `current[17]=-1` without the param and `current[17]=7414` with it added. This affected BOTH PO Analytics and the Offer Analytics export (both share `fetch_products()`) — fixed once in the shared function. See `docs/features/po_analytics.md`'s 2026-10-07b entry for the full session (this was one of 5 fixes landed together there) and `docs/features/vendor_offers.md` for the export side.

**Changes this session (2026-09-23e) — `_call_product` token-exhaustion fix (a multi-hour export dying at the end and losing everything):**
- Full detail in `docs/features/vendor_offers.md`'s 2026-09-23e entry. Summary: Keepa's own recoverable "not enough tokens, retry later" error was being treated as immediately fatal, propagating all the way up and killing a multi-hour export's entire already-completed work with nothing partially saved. Fixed with a 3-layer change: treat "token" errors as retryable with backoff (12 attempts, up from 6), raise the pre-flight token-budget check to scale with batch size, and skip (rather than raise on) a batch that still fails after every retry so the rest of the export can complete.

**Changes this session (2026-09-03) — switched from Keepa's `offers=20` parameter to `buybox=1` to fix a live-export crash:**
- Full detail in `docs/features/vendor_offers.md`'s 2026-09-03 entry. Summary: `offers=20` ships every offer object per ASIN (~50KB each); at 100 ASINs/batch responses hit ~5MB and broke mid-download (`ChunkedEncodingError`), killing a live multi-hour export. `buybox=1` returns just the Buy Box columns actually needed in a ~5KB/ASIN payload. `_bb_window` changed its return shape to a 3-tuple `(top_seller_id, top_pct, amazon_pct)`.

**Changes this session (2026-10-02e) — `discover_sub_brands` confidence-floor fix (noise brands outranking the real seed brand):**
- Full detail in `docs/features/brand_analytics.md`'s 2026-10-02e entry. Summary: the sub-brand-discovery sampler was ranking candidate brands by their GLOBAL Amazon-wide popularity rather than by how strongly they actually co-occurred with the seed brand in the sample, letting unrelated-but-popular brands (BND, PrimeMed) outrank the real result (Safetec). Fixed with a sample-hit-count + sample-share confidence floor before a candidate's global count is even looked up.
