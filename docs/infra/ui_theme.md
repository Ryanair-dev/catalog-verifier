# UI Theme (shared CSS design tokens)

## What this does

The whole app shares one set of CSS design tokens (`:root` variables in `static/styles.css`) and a common set of component classes (`.card`, `.stat-card`, `.btn*`, `.sidebar`/`.nav-item`, `.side-panel`, `.modal-shell`, `.wizard-shell`, `.cs-menu`, `.drop-zone*`, `.toggle`) that every feature's view builds on. Whole-app visual/theme changes belong here rather than being force-fit into one feature's doc, since they're cross-cutting by nature.

## Architecture

Covered implicitly by the Changelog below — there is no separate living design-system spec; `static/styles.css`'s `:root` block itself is the source of truth for current token values.

**Dark mode (since 2026-11-23): `static/dark.css`, GENERATED by `scripts/build_dark_css.py`, switched in Settings > Appearance.**
- On when `<html data-theme="dark">`. The choice is `localStorage["cv-theme"]` (`"light"` / `"dark"`, per browser), applied before first paint by a 1-line inline script at the end of `index.html`'s `<head>`. `applyTheme()` in `app.js` (next to the Settings tab code) flips the attribute, saves it, updates `#theme-dark-switch`, and pushes the theme into the two iframes that have their own palettes (Blacklist, Vendor Offers / Price Desk); a `storage` listener keeps other open tabs in step. Both iframe pages also read `cv-theme` themselves before paint.
- **A real dark palette, generated, not hand-written and not a filter.** The app has ~500 literal colours in `styles.css` / `create_po.css` and ~850 inline `style="..."` colour declarations in `index.html`, `app.js`, `families.js`, `create_po.js`. `scripts/build_dark_css.py` reads them all and writes a dark counterpart for each with ONE colour rule (`map_color`/`map_rgb`): keep the hue, move only the lightness, by the colour's job:
  - background: white cards -> `#1b1e25`; the grey-50 page -> `#14161a` (darker than cards); zebra/hover/chip greys -> a step lighter than cards; pale tints (badges, chips, highlights) -> deep tints of the same hue; solid/mid colours (purple buttons, navy headers) kept.
  - text/icons: dark greys/navy -> light greys; coloured text lifted to 62-72% lightness (readable, not neon); light text (white on purple) kept.
  - borders: light greys -> dark greys a step above the cards; light tints -> mid-dark tints.
  - "Neutral" is decided by chroma, with a tighter cut-off near white (HLS saturation calls `#f7f8fa` 23% saturated).
- **Output sections**, all scoped to `html[data-theme="dark"]` (the scoping is not enforced by the script; it was checked on 2026-11-23, see changelog): (1) the `:root` tokens remapped by name/role (`token_role`: grey-50 page, grey-100..300 borders, grey-500/700 + navy text, `-50/-100` tints, `-600+` text, purple-800/900 kept as dark backgrounds); (2) every colour declaration of `styles.css` and `create_po.css` mirrored with +1 class +1 type specificity, var()-based ones included so their relative cascade is unchanged; (3) inline styles as `[style*="color:#6b7480"]` attribute rules with `!important` (the only way to beat an inline style), longest string last so `background:#fff7ed` beats its prefix `background:#fff`, plus generic per-colour rules for colours picked at runtime in JS and for `el.style` writes (which serialise as `rgb(r, g, b)`); (4) a short MANUAL block (`color-scheme: dark`, the loading car, Tailwind `bg-white`, a few SVG `stroke=` icons, form fields, deeper card shadows).
- **Tokens used in the "other" role** (`resolve_vars`): a token is remapped for one role, so where e.g. `--purple-800` (a dark-background token) is used as heading text, or `--navy-800` (text) as a background, that spot gets the colour mapped for its actual role instead. An undefined token with a fallback (`var(--indigo-600, #4f46e5)`) is treated as its fallback colour.
- **The Offer Analysis loading car** (`lottie-player`, `static/loader-car.json`) is near-black lines on transparent, so dark mode draws it with `filter: invert(1) hue-rotate(180deg)` (white lines). The animation's own "Carregando..." text layer was never readable in light mode either and is unchanged.
- **Price Desk** (`static/price_desk.html`) is token-driven already: it has a hand-written `html[data-theme="dark"]` token block whose values were computed with the same `map_value`, plus a pre-paint `cv-theme` script. **Blacklist** (`static/marketplace_blacklist/`) has its own dark palette; its neutrals were aligned to the app's (`--bg #14161a`, `--surface #1b1e25`, ...).
- **Safety check in the script:** `check_balanced()` refuses to write output with unbalanced braces/parentheses, because one stray `(` silently made the browser drop every later rule (this happened once during the build: an inline `color:var(--teal-600,#0f8a8d)` cut before its `)` swallowed the last ~40 rules, including the car fix).
- **When adding UI with new colours: run `python scripts/build_dark_css.py`** and bump `dark.css?v=` in `index.html`. Colours written through tokens (`var(--grey-700)`, etc.) need nothing. Values built at runtime (`style="color:${c}"`) are covered only if the colour literal appears somewhere in the JS file (the generic per-colour rules).

**2026-10-27** — Fixed a real, pre-existing bug the new Settings "Tasks Running" tab happened to expose: every `.lib-type-tab` across the whole app (Settings, Toolbox, Reports, the Library panel itself) would light up "active" at once. Also widened the Settings panel to match Toolbox.
- User: "when I open the side tab all the tabs are automatically highlighted as if they are clicked on for both the side tabs the settings and toolbox."
- **Root cause**: the Universal Library panel's (`#abbr-panel`) own tab-switching code (`static/app.js`, the click-listener attachment and `_switchLibTab()`) used a bare, unscoped `$$(".lib-type-tab")` — every element with that class ANYWHERE in the document, not just the Library panel's own 3 tabs. Settings/Toolbox/Reports each reuse the same `.lib-type-tab` class for their own, separately-scoped tab bars (`#settings-panel .lib-type-tab` etc.) — so clicking any of THEIR tabs also fired the Library panel's global click handler. That handler calls `_switchLibTab(tab.dataset.libType)`, and since Settings/Toolbox/Reports tabs don't carry a `data-lib-type` attribute at all, `t.dataset.libType === type` evaluated to `undefined === undefined` (true) for every single one of them, marking them ALL `.active` simultaneously. This bug predates today's Settings tab work — it already affected Toolbox's and Reports' own tabs — the new Settings tab is just what made the user notice it.
- **Fix**: scoped both the click-listener attachment and `_switchLibTab()`'s own toggle to `#abbr-panel .lib-type-tab`, matching the pattern every other panel's tab-switcher (`_switchSettingsTab`/`_switchToolsTab`/`_switchReportsTab`) already used correctly.
- **Settings panel widened**: `#settings-panel` gained the `side-panel-wide` class (560px, same as `#tools-panel`/`#abbr-panel`) — it was previously the default (narrower) `.side-panel` width, undersized now that it has real tab content (the Tasks Running tab's job/run/scheduler cards).
- **Verified**: brace/paren/div balance held in both files; confirmed via TestClient that the served `index.html` carries the new class and `app.js` no longer has the unscoped selector in actual code (only in an explanatory comment describing the old bug). Static files only — served directly from disk, no backend restart needed; confirmed live on the running server immediately.
- Scope: `static/app.js`, `static/index.html`. **No backend restart needed.**
