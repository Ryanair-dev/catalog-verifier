# Job Persistence (`background_jobs`)

## What this does

A shared mechanism so in-memory background jobs (PO Analytics report generation, Offer Analytics/Vendor Offers exports, and likely others) survive a server restart instead of silently vanishing mid-run. Confirmed real and shipped (session task list: "Persist + auto-resume all background jobs across server restart" — completed), and referenced from multiple feature docs (`docs/features/po_analytics.md`, `docs/features/vendor_offers.md`) as the system their own job/poll/download endpoints build on.

## Architecture

**Partially documented.** The `background_jobs` table exists (see `docs/infra/database.md`'s schema table) as a "shadow" of whatever in-memory job-state dicts each feature's router keeps (the pattern already established pre-this-feature: `job = {status, phase, done, total, filename, ...}` dicts in module-level `_JOBS`-style maps, polled via `GET .../jobs/{id}`). This persistence layer was evidently added to snapshot that state to SQLite and restore/resume it on the next startup, but the specific mechanics (what triggers a snapshot write, how resume detects an in-flight job and whether it restarts the work from scratch or picks up partway through, which features are actually wired to it) were not present in the source material this documentation restructure was built from — the feature was built in a session after the source `CLAUDE.md`'s last entry (2026-10-16).

**Before changing or extending this**: read `services/database.py`'s `background_jobs` table definition and whichever router(s) actually read/write it (search for `background_jobs` across `routers/`), rather than trusting the summary above as authoritative beyond "the table exists and is used for this purpose."

- **Scoped via a full codebase survey first, not assumed** — found 16 distinct, independently-built state sources with no shared schema and nothing that aggregated them anywhere (frontend or backend): 7 in-memory "start → poll → done" job dicts (Vendor Offers export, PO Analytics export, Seller Analytics, 3 Toolbox checks, Pair Library import), 3 DB-row "run" tables (Offer Analysis `analytics_runs`, Brand Analytics `brand_analytics_runs`, Health Check `health_check_runs`), and 6 recurring schedulers (vendor-offers mailbox sync, PO automation, Azure SQL refresh, MPN check sync, SellerCloud catalog index, health check) — 3 of which (`azure_sql`, `mpn_check_sync`, `sellercloud/catalog_index`) had a `scheduler_status()`-style function that was never actually exposed via any endpoint, and `sellercloud/catalog_index` had no status function at all.
- **New convention established — `list_jobs_for_tasks_panel()`**: each of the 7 job-dict routers (`routers/eligibility.py`, `storage_fees.py`, `generic_check.py`, `po_analytics.py`, `seller_analytics.py`, `pairs.py`, `vendor_offers.py`) gained this small public function, returning a normalized `{feature, job_id, status, phase, done, total, started_at}` snapshot of its private `_JOBS`/`_ANALYTICS_JOBS`/`_IMPORT_JOBS` dict. This is a read-only accessor alongside each file's existing `_get_job()` — no change to how jobs are created, updated, or evicted (the existing 1-hour TTL eviction already gives "recent history" for free; this just reads the live dict).
- **New `services/sellercloud/catalog_index.scheduler_status()`** (this scheduler had none before): tracks `running_now` via a new module-level flag set/cleared around `refresh_snapshot()`, and persists the outcome of each actual refresh ATTEMPT (not every no-op "still fresh" cycle) via `database.set_setting("catalog_index_scheduler_last_run", ...)` — same persisted-JSON-status pattern `vendor_offers_mailbox_sync.py`/`mpn_check_sync.py` already use.
- **New `GET /api/settings/tasks-running`** (`routers/settings.py`): aggregates all three kinds of source into `{jobs: [...], runs: [...], schedulers: [...]}` — calls all 7 `list_jobs_for_tasks_panel()` accessors, queries the 3 run tables directly for their 5 most-recent rows each (covers a currently-running row and recent history in one query, no separate "is it running" status vocabulary needed), and calls all 6 schedulers' `scheduler_status()`. Each source wrapped in its own try/except so one broken source can't blank the whole response.
- **UI** (`static/index.html`/`app.js`): `#settings-panel` was a single flat panel before this — now has a `.lib-type-tabs.tools-tab-bar` tab bar (same CSS/markup pattern as the Toolbox's existing `#tools-panel` sub-tabs) with "Thresholds" (the pre-existing content, now wrapped in `#settings-tab-thresholds`) and new "Tasks Running" (`#settings-tab-tasks`). The new tab polls the aggregation endpoint every 4s via `setInterval`, started on tab-switch-in and stopped centrally in the shared `_closeActivePanel()` (so it can't keep polling in the background after any panel closes, not just this one) — mirrors the existing Toolbox `_switchToolsTab` pattern. Renders three sections (jobs/runs/schedulers) as simple bordered cards, each with a progress bar when `done`/`total` are present, colored by status, with user-supplied text (run names) passed through the existing `escapeHtml()` helper.
