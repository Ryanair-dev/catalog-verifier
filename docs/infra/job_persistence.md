# Job Persistence (`background_jobs`)

## What this does

A shared mechanism so in-memory background jobs (PO Analytics report generation, Offer Analytics/Vendor Offers exports, and likely others) survive a server restart instead of silently vanishing mid-run. Confirmed real and shipped (session task list: "Persist + auto-resume all background jobs across server restart" — completed), and referenced from multiple feature docs (`docs/features/po_analytics.md`, `docs/features/vendor_offers.md`) as the system their own job/poll/download endpoints build on.

## Architecture

**Partially documented.** The `background_jobs` table exists (see `docs/infra/database.md`'s schema table) as a "shadow" of whatever in-memory job-state dicts each feature's router keeps (the pattern already established pre-this-feature: `job = {status, phase, done, total, filename, ...}` dicts in module-level `_JOBS`-style maps, polled via `GET .../jobs/{id}`). This persistence layer was evidently added to snapshot that state to SQLite and restore/resume it on the next startup, but the specific mechanics (what triggers a snapshot write, how resume detects an in-flight job and whether it restarts the work from scratch or picks up partway through, which features are actually wired to it) were not present in the source material this documentation restructure was built from — the feature was built in a session after the source `CLAUDE.md`'s last entry (2026-10-16).

**Before changing or extending this**: read `services/database.py`'s `background_jobs` table definition and whichever router(s) actually read/write it (search for `background_jobs` across `routers/`), rather than trusting the summary above as authoritative beyond "the table exists and is used for this purpose."

The frontend's `_checkBrands()` called this endpoint once per brand with its OWN client-side `Promise.all` 2-worker pool and a purely client-side `#brand-check-progress` counter — nothing on the backend ever created a job, a job_id, or any persisted state at all. `list_jobs_for_tasks_panel()`'s label ("Toolbox: Eligibility / Check Brand") was also just wrong — it only ever read `_JOBS`, which Check Brand never wrote to.
- **Converted Check Brand into a real background job** (`routers/eligibility.py`): extracted the existing single-brand logic into `_run_brand_check(brand, sample_size, sample_pct)` (pure function, no FastAPI dependency) — the original `POST /eligibility/check-brand` is now a thin wrapper around it, unchanged behavior for any other caller. New `POST /eligibility/check-brand/start` (body: `{brands: [...], sample_size, sample_pct}`) creates a job in the same `_JOBS` dict Eligibility Check already uses (tagged `"kind": "brand_check"` so `list_jobs_for_tasks_panel()` can label the two correctly instead of conflating them), and processes the brand list with a `ThreadPoolExecutor(max_workers=2)` background thread — same concurrency the old client-side loop used. New `GET /eligibility/check-brand/jobs/{job_id}` (poll) and `POST .../cancel` (stop picking up new brands; in-flight ones finish) round out the same start/poll/cancel shape every other job type in this app already has.
- **Frontend** (`static/app.js` `_checkBrands()`): rewritten to POST to `/start`, then poll the job every 1s, rendering each brand's result (via the existing `_appendBrandRow`/`_renderSingleBrandResult`, untouched) as it arrives in `results` — same single-vs-bulk UI behavior as before (identical table/single-result rendering, Cancel button, export button), just backed by a real job instead of a client-side loop. `job.total` (server-deduplicated brand list) is used for the progress count instead of the frontend's raw pre-dedup list length, so "N / M checked" can't go stale if the input had a duplicate brand name.
- **Verified end-to-end** with `_run_brand_check` mocked (no real SP-API/Keepa spend): start → poll sequence showed progress advancing (`0/3` → `2/3` → `complete 3/3`) with all 3 results present; cancel mid-run correctly left `done` at whatever had completed and set `status: "cancelled"`; confirmed a `running` Check Brand job is now correctly visible via `GET /api/settings/tasks-running` as `{"feature": "Toolbox: Check Brand", "status": "running", ...}` — the exact gap reported. Checked the live server's own request log before restarting to confirm no brand check was actually in flight on the old (blocking) endpoint that a restart would have cut off.
