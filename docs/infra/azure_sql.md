# Azure SQL (`services/azure_sql.py`)

## What this does

Read-only mirror of the live SellerCloud catalog (and, separately, a Monday.com board mirror used by PO Analytics — see `docs/features/po_analytics.md`'s `services/monday_eta.py`) held in Azure SQL. The primary consumer is Create SKUs (catalog existence/prefix lookups) and PO Analytics (Main SKU → FBA/FBM child resolution); both prefer this live source over the older local xlsx snapshot, which repeatedly caused staleness bugs.

## Architecture

- `fetch_rows()` — pulls `[analytics].[sku_data_extended_view]` (~180k rows across all companies), 30-min in-process cache (superseded by the hourly scheduler below, which keeps it warm proactively instead of lazily). Columns include `Status` (Active/Disabled — added 2026-10-07f) and `CompanyName`.
- `catalog_index(company)` / `brand_map(company)` / `catalog_source(company)` — company-scoped views over the cached rows, used by Create SKUs. `_rows_for_company(company)` filters by `CompanyName`, with a `_COMPANY_UNION` override: `"Turba"` returns the UNION of `"Ford Medical, LLC"` and `"Turba"` rows, since the vast majority of Turba's catalog is Amazon/Merchant shadow listings of a shared Ford Medical main (a pure Turba-only scope would wrongly treat that shared main as "new" for a Turba batch) — see `docs/features/create_skus.md`, 2026-10-08b.
- `start_scheduler()` / `stop_scheduler()` / `scheduler_status()` — hourly daemon thread (mirrors `services/vendor_offers_db_sync.py`'s pattern) that force-refreshes `fetch_rows()` every hour regardless of demand, then refreshes `sc_reference`'s brand-prefix/manufacturer tables from the same pull. Wired into `main.py`'s lifespan (replaced an earlier one-shot startup-only warm thread). A failed pull is logged and retried next cycle, never crashes the thread.
- `is_configured()` — used by callers (e.g. PO Analytics' `gather()`) to raise a clear error instead of silently degrading to a stale fallback when Azure isn't reachable (see 2026-10-07e in `docs/features/create_skus.md` — the local-snapshot fallback was removed project-wide per explicit user instruction).

**Honest ceiling**: an hourly refresh closes the gap between "Azure's own mirror updated" and "we noticed" — it does NOT speed up how fast Ford Medical's own Azure ETL reflects a change made directly in SellerCloud's UI, which is outside this codebase and unverified from here.

## Changelog

**Changes this session (2026-10-07c) — Azure catalog mirror: hourly background refresh instead of a 30-min lazy TTL:**
- Follow-on to 2026-10-07b's live-Azure switch for PO Analytics. User: "why dont we jst constantly update it? ... have it run every once an hour" — the existing 30-min in-process cache (`services/azure_sql.py fetch_rows`) only refreshes WHEN something happens to call it again after the TTL expires; between on-demand PO Analytics/Create SKUs runs nothing was proactively refreshing it, which is exactly how the local xlsx snapshot (a different, older data path) sat 56 days stale earlier today with nobody noticing — the same silent-staleness risk existed here too, just bounded to 30 min instead of indefinitely.
- **New `azure_sql.start_scheduler()`/`stop_scheduler()`/`scheduler_status()`**, mirroring `services/vendor_offers_db_sync.py`'s exact hourly-scheduler shape (daemon thread, `threading.Event`s for stop/running, `INTERVAL_SECONDS=3600`): force-refreshes `fetch_rows()` every hour regardless of demand, then also refreshes `sc_reference`'s brand-prefix/manufacturer tables from the SAME pull (`force=False` — reuses the rows just pulled instead of a 2nd full query). Best-effort: a failed pull is logged and retried next cycle, never crashes the thread.
- **`main.py`'s lifespan** now calls `azure_sql.start_scheduler()` in place of the one-shot startup-only warm thread it had before — the scheduler's own first loop iteration runs immediately (not after the first hour), so startup behavior is unchanged (still warms the cache right at boot) but now also recurs hourly afterward, so **any caller (PO Analytics, Create SKUs, sc_reference) almost always finds an already-warm (<1h) cache** instead of paying the ~165s pull cost inline.
- **Verified live**: started the scheduler directly, confirmed it connects to Azure and begins a real pull without crashing (`scheduler_status()["running_now"]` flips `True` during the pull, `scheduler_alive` stays `True`).
- **Honest ceiling, explained to the user**: this closes the gap between "the upstream Azure view updated" and "we noticed" — it does NOT change how fast Ford Medical's own Azure ETL itself reflects a change made directly in SellerCloud's UI, which is outside this codebase and unverified from here. An hourly refresh means a SellerCloud-side change is visible here within ~1 hour of whenever Azure's own mirror picks it up, not ~1 hour of the SellerCloud edit itself.
- Scope: `services/azure_sql.py` (scheduler added), `main.py` (one-shot warm thread replaced with the scheduler call). **Needs a backend restart.**
