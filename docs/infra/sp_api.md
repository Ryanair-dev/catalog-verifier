# SP-API (`services/spapi/`)

## What this does

Amazon Selling Partner API client used across the whole app for catalog search (Offer Analysis, Brand Analytics, Quick Search), eligibility/restrictions checks (Toolbox), and reports (PO Analytics' 30-day sales). Supports multiple seller-account "stores" (Priority Pharmacy default + Turba) with independent credentials and rate-limit buckets.

## Architecture

- `services/spapi/client.py` — `CatalogAPI` HTTP client; `get_catalog_api(marketplace, store="default")` is store-aware. `MultiStoreCatalogAPI` round-robins `search_by_identifiers`/`search_by_keywords`/`search_by_brand_names`/`get_by_asin` across however many stores are configured (degrades to single-store automatically; raises only if none configured) — safe because catalog SEARCH is Amazon's public catalog data, identical regardless of which seller account's credentials make the call, so round-robining just draws from two independent rate-limit buckets instead of one. `get_multi_store_catalog_api()` factory. `lease_catalog_api(marketplace="US") -> CatalogStoreLease` (added 2026-10-20, see Changelog) is a DIFFERENT, coarser mechanism: a per-JOB store assignment (not per-request round-robin) so two concurrent getCatalogItem-heavy BATCH jobs land on two different stores' rate buckets for their whole run, each via a module-level `_lease_counts` dict guarded by `_lease_lock` (in-memory only, resets on restart — a soft load-balancing hint, not a hard allocation).
- `services/spapi/auth.py` — LWA token refresh, per-store credentials.
- `services/spapi/catalog.py` — `search_by_identifiers`/`search_by_keywords`/`search_by_brand_names`/`get_by_asin` wrappers. `_get` retries transient network errors and 500/502/503/504 with backoff (not just HTTP 429) — see Changelog, 2026-08-18k. Its retry/backoff is cancellation-aware via an optional `should_cancel` param (added 2026-10-20, see Changelog) — `SPAPICancelled` is a back-compat alias for `services/cancellation.py`'s `JobCancelled`, the shared exception + `cancellable_sleep` helper also used by `services/restrictions.py` and `services/keepa.py`'s own retry loops.
- `services/spapi/config.py` — `_STORES` registry (`default` = Priority Pharmacy, `turba` = Turba), each with its own env-var name list; `load_sp_api_credentials(store="default")`; `list_stores()` reports per-store `configured`/`seller_id_configured` (split apart since a store can have working catalog search but no seller ID for eligibility).
- `services/spapi/rate_limiter.py` — `new_limiters()` factory builds a genuinely independent per-store token-bucket set; `LIMITERS` is the default/shared instance for back-compat. `CatalogAPI`/`RestrictionsAPI` (`services/restrictions.py`) both take a `limiters` constructor param. Each bucket records `last_foreground` (acquires outside `background_use()`); `foreground_idle_seconds()` reports how long the default store has been idle (used by `services/eligibility_warmer.py`).
- `services/restrictions.py` — eligibility/restrictions checks (`getListingsRestrictions`). Deliberately NOT round-robined across stores — restrictions are genuinely seller-scoped data, not interchangeable between accounts. `get_restrictions_api(store="default")` is a plain per-store selector. See `docs/features/toolbox.md` for the Eligibility Check feature built on this (that tool's eligibility checks remain ALWAYS LIVE, never cached, by its own long-standing design). Also carries `eligibility_cache_get`/`eligibility_cache_put` (7-day TTL `eligibility_cache` table) — an OPT-IN cache only `services/vendor_offers_template_export.py enrich_asins` currently calls, added 2026-10-19 (see Changelog).
- `services/spapi/reports.py` — Reports API (`GET_SALES_AND_TRAFFIC_REPORT`), used by PO Analytics for 30-day unit sales — see `docs/features/po_analytics.md`.

**2026-10-20 — Concurrent batch getCatalogItem jobs now split across stores (PPP vs Turba) instead of sharing one rate budget:**
- Context: the user reported real `[429] Throttled on getCatalogItem` log spam during a Vendor Offers export, and asked (after confirming it was expected single-store throttling, not a Keepa-style cost-estimate bug — see this file's own earlier investigation in conversation) "can we make it so that if there are like 2 get catalog requests using at the same time, then we split it. Meaning to one they use the PPP api and for the second analytics we use the turba." Confirmed BEFORE building anything that Turba's credentials (`AMZ_CLIENT_TRB_*`) actually ARE set in `.env` (an earlier grep pass had a false negative from a stray space before `=` in the file — corrected by re-checking with a looser pattern), so this was genuinely buildable, not a no-op.
- **New `services/spapi/client.lease_catalog_api(marketplace="US") -> CatalogStoreLease`**: a per-JOB (not per-request) store assignment. Picks whichever CONFIGURED store currently has the fewest other active leases (`default` wins ties), increments its lease count, and returns a `CatalogStoreLease` (use as `with lease_catalog_api() as capi:`, or call `.release()` manually — idempotent). A lone job still gets `"default"` (Priority Pharmacy) only; `"turba"` is only handed out when something else already holds `"default"`'s lease at that moment — this never speeds up a single job, it only keeps two concurrent ones from fighting over one store's 2 req/sec getCatalogItem ceiling. Exported from `services/spapi/__init__.py` alongside the existing `get_catalog_api`/`get_multi_store_catalog_api`.
- **This is deliberately a DIFFERENT mechanism from `get_multi_store_catalog_api`**, not a replacement: the multi-store round-robin alternates every individual REQUEST across stores to roughly double ONE job's own throughput (used by catalog search today); the lease pins one job's ENTIRE run to one store's credentials/budget for its whole duration, so two independent jobs' worth of getCatalogItem calls never land in the same bucket. Both can coexist; nothing about the existing round-robin search path changed.
- **Wired into every batch (not single-ASIN-lookup) getCatalogItem consumer**: `services/vendor_offers_template_export.py enrich_asins()`, `services/analytics/po_analytics.py` (PO Analytics dimension enrichment), `services/analytics/brand_runner.py` (both `_keepa_brand_pipeline` and `_brand_pipeline` now take a `catalog` parameter instead of calling `get_catalog_api()` themselves, so `start_brand_run` leases ONE store for the whole run — covering both the Keepa-enrichment catalog calls and the SP-API search/getCatalogItem phases together), and `services/health_check.py run_health_check` (the weekly Pair Library job). Deliberately left OUT of the single-ASIN, user-triggered Toolbox endpoints (`routers/eligibility.py`, `services/generic_check.py`, `routers/storage_fees.py`) and `services/analytics/po_analytics.py`'s other `get_catalog_api()`-adjacent callers that aren't batch loops — those make at most a handful of calls per click and aren't the source of sustained rate pressure, so adding lease bookkeeping there would be pure overhead with no real benefit.
- **Verified**: a scripted test acquiring leases sequentially confirmed job 1→`default`, job 2 (while job 1 still held)→`turba`, job 3 (while both held)→`default` (tie-break), and a lone job after full release→back to `default`. A second test launched two real threads concurrently (each acquiring a lease, blocking on a `threading.Barrier`, holding it 0.3s, then releasing) and confirmed they landed on `{"default", "turba"}` — one each, not both on the same store. Full app re-imports cleanly via FastAPI TestClient after the refactor (all 6 touched files: `services/spapi/client.py`, `services/spapi/__init__.py`, `services/vendor_offers_template_export.py`, `services/analytics/po_analytics.py`, `services/analytics/brand_runner.py`, `services/health_check.py`).
- **Restart needed**: yes — this changes background-thread Python code paths (not just static files), so the running server must be restarted to pick it up. Deliberately NOT restarted immediately in this session because the user had a live Vendor Offers export in flight they didn't want interrupted; mirrored to the live checkout and verified importable there, restart left for the user's own timing.

**2026-10-19 — `services/restrictions.py` gained an opt-in 7-day eligibility cache, used ONLY by the Vendor Offers export pipeline:**
- User (mid-conversation, while discussing the Vendor Offers export's Keepa/eligibility phase ordering): "could you please cache eligiblility for 1 week, and keepa data for 2 days." See `docs/infra/keepa.md`'s own 2026-10-19 entry for the Keepa half.
- **This is a real reversal of a long-standing, repeatedly-confirmed design decision**, worth stating plainly: this project has an extensive history (`docs/features/toolbox.md`'s own Changelog, 2026-09-03/09-04) of the Toolbox's standalone "Eligibility Check" tool being explicitly, deliberately ALWAYS LIVE — a past investigation confirmed two real consecutive-day answers for the same ASIN genuinely differed because Amazon's own gating had changed, and the user wanted to keep seeing that in real time. This new cache does **NOT** touch that tool or its guarantee. It's scoped specifically to `services/vendor_offers_template_export.py enrich_asins()` (and therefore also PO Analytics + Seller Analytics, which reuse that same function) — the pipeline this whole conversation was about — because the request came up specifically in that context, not as a blanket "cache eligibility everywhere" instruction. If the user wants it extended to the Toolbox tool too, that's a distinct, explicit ask, not assumed here.
- **New `eligibility_cache` table** (`asin TEXT PRIMARY KEY, status TEXT, as_of TEXT`) + `eligibility_cache_get`/`eligibility_cache_put` (`_ELIGIBILITY_CACHE_TTL_DAYS = 7`), same shape as the existing storage-fee cache pattern. `classify()`/`get_restrictions_api()` themselves are completely UNCHANGED — this is a separate, parallel caching layer that a caller opts into explicitly by calling these two new functions around its own `classify(...)` call; every other existing caller of `classify`/`get_restrictions_api` is unaffected.
- **A fresh DOG finding always overrides a stale cached eligibility value** (`enrich_asins`'s own `one()` only consults the eligibility cache `if e != "DOG"`, i.e. only when the live catalog call this same pass didn't already find the ASIN delisted) — a cache entry can never make an ASIN that's since gone dead look falsely "still eligible." Every newly-determined (or corrected) eligibility result is written back to the cache, refreshing its timestamp; a value that was itself just read FROM the cache is never re-written (so cached entries actually age out and eventually refresh, rather than perpetually renewing themselves).
- **Honest tradeoff, not hidden**: Amazon's own brand-gating can genuinely change within a week (the exact scenario the earlier "always live" investigation confirmed happens in practice) — a cache hit may report a status that's since changed. This is the user's own explicit, deliberate choice for this specific pipeline.
- **Verified live**: cleared both the eligibility AND storage caches for 3 real ASINs, confirmed a cold `enrich_asins()` call takes real time (4.7s) and returns correct live eligibility (`CAN_SELL` for all 3, confirmed against real Amazon data); an immediate second call for the same 3 ASINs returned byte-identical results in 0.0s (full cache hit on both eligibility and storage simultaneously).
- Scope: `services/restrictions.py` (`eligibility_cache_get`/`eligibility_cache_put`/`_ensure_eligibility_cache_table`/`_ELIGIBILITY_CACHE_TTL_DAYS` added; new `datetime`/`services.database` imports), `services/vendor_offers_template_export.py` (`enrich_asins`'s `one()` rewritten to consult/update the cache; `eligibility_cache_get`/`_put` called once each per `enrich_asins` invocation). **Needs a backend restart.**
