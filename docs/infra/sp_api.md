# SP-API (`services/spapi/`)

## What this does

Amazon Selling Partner API client used across the whole app for catalog search (Offer Analysis, Brand Analytics, Quick Search), eligibility/restrictions checks (Toolbox), and reports (PO Analytics' 30-day sales). Supports multiple seller-account "stores" (Priority Pharmacy default + Turba) with independent credentials and rate-limit buckets.

## Architecture

- `services/spapi/client.py` — `CatalogAPI` HTTP client; `get_catalog_api(marketplace, store="default")` is store-aware. `MultiStoreCatalogAPI` round-robins `search_by_identifiers`/`search_by_keywords`/`search_by_brand_names`/`get_by_asin` across however many stores are configured (degrades to single-store automatically; raises only if none configured) — safe because catalog SEARCH is Amazon's public catalog data, identical regardless of which seller account's credentials make the call, so round-robining just draws from two independent rate-limit buckets instead of one. `get_multi_store_catalog_api()` factory.
- `services/spapi/auth.py` — LWA token refresh, per-store credentials.
- `services/spapi/catalog.py` — `search_by_identifiers`/`search_by_keywords`/`search_by_brand_names`/`get_by_asin` wrappers. `_get` retries transient network errors and 500/502/503/504 with backoff (not just HTTP 429) — see Changelog, 2026-08-18k.
- `services/spapi/config.py` — `_STORES` registry (`default` = Priority Pharmacy, `turba` = Turba), each with its own env-var name list; `load_sp_api_credentials(store="default")`; `list_stores()` reports per-store `configured`/`seller_id_configured` (split apart since a store can have working catalog search but no seller ID for eligibility).
- `services/spapi/rate_limiter.py` — `new_limiters()` factory builds a genuinely independent per-store token-bucket set; `LIMITERS` is the default/shared instance for back-compat. `CatalogAPI`/`RestrictionsAPI` (`services/restrictions.py`) both take a `limiters` constructor param.
- `services/restrictions.py` — eligibility/restrictions checks (`getListingsRestrictions`). Deliberately NOT round-robined across stores — restrictions are genuinely seller-scoped data, not interchangeable between accounts. `get_restrictions_api(store="default")` is a plain per-store selector. See `docs/features/toolbox.md` for the Eligibility Check feature built on this.
- `services/spapi/reports.py` — Reports API (`GET_SALES_AND_TRAFFIC_REPORT`), used by PO Analytics for 30-day unit sales — see `docs/features/po_analytics.md`.

**Changes this session (2026-08-18k) — Tools: eligibility/storage/generic flakiness fixed (SP-API HTTP layer now retries transient failures):**
- User: on a 3,789-ASIN Tools run, ~19 ASINs had an EMPTY storage fee (+20 eligibility ERROR, +6 generic Error); re-running found the dims. Diagnosed NOT missing data — re-fetched the "empty" ASINs (B0053GYCGE/B00EZWTY42/B00HRQQNCO) 3× each, all returned dims consistently. Root cause: **the SP-API HTTP layer only retried HTTP 429**; a `requests` network error (timeout / connection reset) or a 5xx propagated immediately → the per-ASIN worker caught it as empty/ERROR. Over a long bulk run those are near-certain; a low-load re-run succeeds. Fix: hardened **`services/spapi/catalog.py` `_get`** AND **`services/restrictions.py` `_get`** to (a) wrap `requests.get` in try/except `requests.RequestException` → retry with backoff, (b) retry **500/502/503/504** with backoff (was `raise_for_status`), (c) cap backoff at 30s and raise the request timeout 15→25s. Also hardened **`services/generic_check.py` `_validation_preview`** PUT loop (wrap in try/except + retry 429/5xx, 6 attempts). This covers all three Tools checks (storage + generic use catalog `_get`; eligibility uses restrictions `_get`). Verified the happy path still works for all three on B0053GYCGE. **Backend restart to apply.** NOTE: a genuinely dimensionless ASIN still (correctly) shows an empty fee; the fix only stops transient failures from masquerading as one.
