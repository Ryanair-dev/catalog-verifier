# Reports

## What this does

A new top-level sidebar section (`#reports-panel`, same slide-in-panel-with-sub-tabs architecture as Toolbox) meant to hold "a lot of dashboards" over time. The first dashboard is **PO P&L**: for every Purchase Order assigned to a given person (Avi Schoemann by default) on the Inbound Shipments Monday board, shows how much was bought, how much has sold, and how much is left — in both units and dollars — filterable by vendor/PO#/brand/item, split into an **Active** view (not yet fully sold through) and an **Archive** view (100% sold out), per the user's own stated rule.

## Architecture

- **`services/monday_eta.py`** gained a `purchaser` field (Monday column `purchaser3`, titled "Purchaser" — a PEOPLE column, confirmed live it can hold several names at once, e.g. "Mason Bennet, Avi Schoemann, Victoria Romanoff") and `pos_for_purchaser(name)` — returns the PO numbers of every CURRENT (live, non-archived) Inbound Shipments board item whose Purchaser text contains `name` (substring match, not "sole assignee only"). **Known gap, not yet solved**: this only sees items on the LIVE board — a PO that's since been archived off that board (the team has done this before, see this file's own earlier "Archive 4" note) won't be found by purchaser even if it still has real P&L data sitting in the cash-cycle view below.
- **`services/reports_po_pnl.py`** (new) — the actual PO P&L computation. Data source: Azure's **`analytics.fulfilled_po_to_order_cash_cycle`** view, NOT a live Keepa/SP-API pull. This view is a pre-built FIFO allocation + forecasting engine that already solves the hard problem this dashboard needs: Amazon pools FBA inventory by ASIN, not by PO/lot, so there's no native "which PO did this unit ship from" signal anywhere in Amazon's own data — someone has already built that allocation (oldest-unsold-PO-first) at the data-warehouse level, and it even carries forward-looking FORECAST rows (`ship_date` in the future, `cash_in_source='Forecast'`) for units that haven't sold yet.
  - Columns used: `po_number`, `vendor`, `product_id` (the SellerCloud Main SKU), `received_date`, `qty_received`, `unit_cost`, `cash_out` (= qty×cost for that allocation slice), `ship_date`, `allocated_qty`, `cash_in`, `allocated_profit`, `customer` (the channel/customer a slice sold to).
  - **Critical row-level fact, confirmed live against real PO 51563**: `qty_received` is REPLICATED across every allocation-slice row for a given `(po_number, product_id)` pair — it's a constant per group, so it must be `MAX()`'d, never `SUM()`'d. `cash_out`/`allocated_qty`/`cash_in`/`allocated_profit` are each that ONE slice's own share and DO sum correctly across the group (verified: `SUM(allocated_qty)` across every slice for one pair equals its `qty_received` exactly).
  - **"Sold"** = `SUM(allocated_qty) WHERE ship_date IS NOT NULL AND ship_date <= today` — a row with a FUTURE `ship_date` is a forecast/projection, not a real sale yet, and is deliberately excluded from "sold" (those units still count as "left," since they're still physically on the shelf right now). **"Left"** = `qty_received − sold_qty`.
  - **"Amazon" sold** is approximated as `customer = 'FBA'` — confirmed live this is the only Amazon-labelled value across 618k rows (no separate 'FBM'/'Amazon' value exists in this view). **Not yet confirmed**: whether FBM sales are folded into 'FBA' here, counted under some other customer label, or genuinely absent — flagged, not assumed.
  - `po_number IS NOT NULL` alone correctly scopes to real vendor POs: confirmed live that of the view's 9 `source_type` values, only `'Purchase'` (440,465 rows) and `'Prepaid PO'` (2,702 rows) ever carry a `po_number` — every other type (`Warehouse Adjustment`, `FBA Adjustment`, `Transfer`, `Opening`, `No Supply`, `Adjustment`, `Add Product`) always has it NULL.
  - **Brand/ASIN enrichment**: joins `product_id` against the shared `azure_sql.catalog_index("Ford Medical")` (the same cached catalog index Create SKUs/PO Analytics already use) for `BrandName`, and resolves each Main SKU's FBA/FBM child ASIN(s) via a **custom one-pass reverse-suffix match** (`_ROOT_SUFFIX_RE`), NOT by calling `CatalogIndex.children_for_main()` per line item — that call is itself an O(catalog-size) scan, and calling it once per line item was the actual perf bug found during this build: **32s for ~2,500 line items against a ~115k-row catalog (O(n·m))**, fixed by building one `{root_sku: {asins}}` map in a single pass (`<1s`) using the SAME shadow-child suffix grammar `children_for_main` uses, just applied in reverse (strip the trailing `_QY{n}-FB[AM](?:TRB)?\d*` pattern off a full SKU to recover its root, instead of generating candidate full SKUs from a known root and checking each one).
  - **Caching**: `_enriched_lines_for(purchaser)` caches the full brand/ASIN-enriched line-item list per purchaser for 5 minutes (`_CACHE_TTL`) — not because `catalog_index()` itself is slow (it's a SHARED, hourly-refreshed Azure cache every other feature in this app already relies on being warm), but so retyping a filter box in the dashboard doesn't re-pay the Monday lookup + cash-cycle query + enrich pass on every keystroke. `refresh=True` bypasses it (wired to the UI's Refresh button).
  - `get_po_pnl(purchaser, vendor, po_number, brand, item, bucket, refresh)` → `{"pos": [...], "summary": {...}}`; `get_filter_options(purchaser)` → distinct vendors/brands within that purchaser's scope, for the UI's filter dropdowns.
- **`routers/reports.py`** (new) — `GET /api/reports/po-pnl` (query params mirror the service function 1:1), `GET /api/reports/po-pnl/filters`. Registered in `main.py`. Future dashboards register their own `GET /api/reports/...` endpoints in this same router/file.
- **UI** (`static/index.html` `#reports-panel`, `static/app.js`) — a new sidebar nav item ("Reports", `#open-reports-btn`) opens the panel via the same generic `_openPanel`/`_closeActivePanel` helpers Toolbox/Library/Settings already use. The panel has its own sub-tab bar (`.reports-tab-bar`, a NEW class extending the SAME icon-pill tab CSS Toolbox's `.tools-tab-bar` already defined — both selectors now share one rule set in `static/styles.css`, so any future panel with sub-tabs can extend the same pattern instead of inventing its own look) with "PO P&L" as the only tab today. The PO P&L pane: 4 filter controls (Vendor/Brand `<select>`, PO#/Item free-text, debounced on input) + an Active/Archive `.toggle-pill` + 5 summary stat tiles (POs/Bought/Sold/Profit/Left) + a sortable-by-received-date table where clicking a PO row expands an inline nested table of its own line items (SKU/brand/ASIN/qty+$ bought-sold-left).

## Changelog

**2026-10-19** — Built from scratch, end to end, in one session.
- User: "We need to add a reports tab - there will be a lot of dashboards that we will be able to see. One of them we need is the PNL for POs. So for every Purchase order that is placed and is assigned by Avi on the inbound shipments board. We would need filters like by vendor, by PO number, by brand, by item and we would need to see the sales how much of the po was bought for how much sold and how much is left."
- **Investigated before building anything**: confirmed the "Purchaser" people-column (`purchaser3`) on the live Inbound Shipments Monday board, with "Avi Schoemann" as a real value (164+ occurrences, usually alongside other names). Searched Azure's full table list for anything Purchase/Order/Sales-shaped and found **`analytics.fulfilled_po_to_order_cash_cycle`** — a complete, already-built FIFO PO-to-sale allocation + forecasting view, which turned out to be exactly the data this dashboard needed and made a from-scratch FIFO model (the alternative, much bigger build) unnecessary.
- **Asked the user 4 clarifying questions before writing code** (via AskUserQuestion): how to compute sold/left given Amazon doesn't track per-PO inventory; units vs. dollars (answered: both); historical scope (answered: not a time window — split into an Active dashboard and a 100%-sold-out Archive dashboard instead, which is what got built); whether Reports should be a new top-level sidebar section like Toolbox (confirmed yes). The user's own answer to the sold/left question ("we need to use multiple tables in our azure tables together... the POs qty we received for each item and how much we sold the child sku which has asin on amazon") pointed directly at the Azure-join approach rather than a live SP-API pull, which led to finding the cash-cycle view.
- **Found and fixed a real perf bug during the build, not after**: the first version of brand/ASIN enrichment called the existing `CatalogIndex.children_for_main()` once per line item — correct, but that function is itself an O(catalog-size) linear scan, so calling it ~2,500 times against a ~115k-row catalog took **32 seconds**. Rewrote it as a single one-pass reverse-suffix match (strip the known shadow-child suffix grammar off every SKU once, building one `{root: {asins}}` map) — same correctness (cross-checked against `children_for_main`'s own output on a real SKU, `OFF018107` → `B014TDI4GA`, both before and after the rewrite), under 1 second after.
- **Verified live, end to end, against real production data** (not mocked): for Avi Schoemann's current PO scope — **230 active POs** ($5.98M bought, $2.2M sold, $640K realized profit, $4.3M remaining inventory value at cost) and **10 fully-sold-out archived POs** ($35.7K bought, $49.3K sold, $13.7K profit, correctly $0 left on every one). Spot-checked one archived PO (49101, DJO LLC) by hand: `qty_received=6`, `sold_qty=6`, `left_qty=0` — a real, complete sell-through. Confirmed the full HTTP pipeline (`GET /api/reports/po-pnl`, `GET /api/reports/po-pnl/filters`) end to end via FastAPI TestClient against live Azure, and the router's own JSON-serialization/query-param wiring separately via a stubbed-service test.
- **Not yet done / explicitly flagged, not guessed**: (1) the Purchaser-filter live-board-only gap above; (2) whether FBM sales are correctly represented under the `customer='FBA'` Amazon marker or missed/mislabeled; (3) no Teams/email notification on this dashboard (a separate, already-tracked, still-blocked ask — see `docs/features/vendor_offers.md`'s 2026-10-19 entry on the same missing webhook/email-recipient pattern, though PO P&L itself was never asked to email anything); (4) sorting/column-customization in the table is fixed (received-date desc) — no user-driven re-sort yet.
- Scope: `services/monday_eta.py` (`purchaser` field + `pos_for_purchaser`), `services/reports_po_pnl.py` (new), `routers/reports.py` (new), `main.py` (router registration), `static/index.html` (`#reports-panel` + sidebar nav item, cache-bust `styles.css?v=18→19` / `app.js?v=69→70`), `static/app.js` (panel open/close/tab-switch + the full PO P&L fetch/render/filter/expand logic), `static/styles.css` (`.reports-tab-bar` extends the same pill-tab rules `.tools-tab-bar` already had). **Needs a backend restart** (Python changed in 4 files) + browser hard-refresh.
