# Brand Analytics

## What this does

User enters a brand or manufacturer name; AI discovers sub-brands; Keepa's Product Finder (preferred, when configured) or SP-API keyword-searches for all their ASINs; results include BSR, UPC, EAN, GTIN, MPN, pack/UOM, storage fee, buy box, eligibility. Results cached in DB (7-day freshness). AI Fill extracts missing identifiers from title/description.

## Architecture

### API endpoints (`routers/brand_analytics.py`)

| Method | Path | Notes |
|---|---|---|
| `GET` | `/api/brand-analytics/library` | List brand_library entries |
| `POST` | `/api/brand-analytics/library` | Upsert entry (UNIQUE on name) |
| `DELETE` | `/api/brand-analytics/library/{id}` | Remove entry |
| `POST` | `/api/brand-analytics/discover` | AI sub-brand discovery; auto-saves to library; returns `{cached, result}` |
| `POST` | `/api/brand-analytics/runs` | Create + start run. Body: `{name, search_type, search_terms[], min_rank, max_rank, pages_per_brand, force_refresh}`. Returns `{cached, run_id}` or cache notice. |
| `GET` | `/api/brand-analytics/runs` | List runs (newest first) with `item_count`. Paginates client-side 10/page in the UI. |
| `GET` | `/api/brand-analytics/runs/{id}` | Run detail + paginated items. Params: `limit`, `offset`, `search`, `sort_key`, `sort_dir`. Returns `{run, items, total_items, filtered_count, stats}`. |
| `POST` | `/api/brand-analytics/runs/{id}/control` | Body `{action}` = pause/stop/resume |
| `DELETE` | `/api/brand-analytics/runs/{id}` | Stop + delete run + items |
| `PATCH` | `/api/brand-analytics/runs/{id}/items/{asin}` | Body `{mpn?, upc?, ean?, gtin?}` — manual identifier edit. Only explicitly-provided fields are updated (uses `model_fields_set`). Corrections also written to `asin_identifier_overrides` for global persistence. |
| `POST` | `/api/brand-analytics/runs/{id}/ai_fill` | Start AI Fill background thread (uses claude-haiku; GPT-4o-mini fallback). Column-selectable (MPN/UPC/EAN/GTIN). |
| `GET` | `/api/brand-analytics/runs/{id}/export` | Excel download (columns: Brand, ASIN, Title, BSR, BSR Category, UPC, EAN, GTIN, MPN, AI UPC, AI EAN, AI GTIN, AI MPN) |
| `GET` | `/api/brand-analytics/runs/{id}/categories` | Returns `{categories:[{category, count}]}` grouped by bsr_category, ordered by count desc. NULL mapped to `(No category)`. |
| `POST` | `/api/brand-analytics/runs/{id}/filter-categories` | Body `{remove_categories:[...]}`. Permanently deletes items whose bsr_category matches. `(No category)` removes NULL rows. Returns `{deleted, remaining}`. |
| `GET` | `/api/brand-analytics/runs/{id}/brand-names` | Distinct `amz_brand` (the actual Amazon brand field value found) counts, ordered by count desc — surfaces brand-registry variants beyond the literal search term(s). |

#### Cache freshness logic
- `last_asin_updated_at` < 7 days → returns `{cached:true, age_days, run_id, message}` — UI shows "Use Cached" / "Re-run"
- `last_asin_updated_at` 7–150 days → returns `{cached:true, stale:true, age_days, run_id}` — UI shows choice modal
- > 150 days → auto re-runs (falls through)
- `force_refresh: true` in POST body skips cache check entirely

### Brand runner (`services/analytics/brand_runner.py`)

- **Discovery source**: when Keepa is configured (`services/keepa.py`), discovery runs via Keepa's Product Finder (`find_asins`) — this beats SP-API's keyword-search recall ceiling by a wide margin (e.g. a Medline manufacturer run: SP-API ~6,280 ASINs vs Keepa ~31.5k) because Keepa queries structured brand/manufacturer fields exactly. Keepa's finder caps at 10,000 ASINs/query with no deeper pagination, so `find_asins` recursively partitions the search on `trackingSince` until each partition is ≤10k, then merges+dedupes. Enrichment after Keepa discovery is HYBRID: a batch `searchCatalogItems` call (fast, but SP-API silently drops ~half of a batch's ASINs — variation-sibling collapsing, confirmed live) followed by a single `getCatalogItem` recovery pass for every ASIN the batch dropped.
  - Every Keepa search term is also searched as BOTH `brand` AND `manufacturer` fields (never either/or) — a single combined query would narrow results via Keepa's AND-within-selection semantics, the opposite of what's wanted.
  - When Keepa IS configured, it still runs FIRST but does NOT short-circuit the rest of the pipeline — it falls through into the SAME SP-API keyword+brandNames search (Phases A-D below) as a supplement, not a fallback, since Keepa's own structured brand/manufacturer field can be blank/wrong on real listings that a keyword search would still find.
  - `_keyword_for_search(brand_name)` strips ` by ` (e.g. "Cryotherapy by DonJoy" → "Cryotherapy DonJoy") for cleaner Amazon keyword searches, while keeping the original name for brand fuzzy-matching.
  - BSR and estimated-units-sold-per-month filters apply directly inside the Keepa finder query (`current_SALES_lte`/`current_SALES_gte`, `monthlySold_gte`/`monthlySold_lte`) for **zero extra Keepa tokens** — this is strictly cheaper and faster than filtering after discovery.
  - `discover_sub_brands`/`discover_entities` (`services/keepa.py`) sample real Keepa product data (brand/manufacturer field values actually seen on products matching a seed) to surface genuine sub-brands/registry-name variants with real product counts, rather than relying purely on AI world-knowledge guesses — a confidence floor (≥3 raw sample hits AND ≥2% of all samples examined) filters out coincidental noise brands before spending a token looking up their global popularity.
- **When Keepa is NOT configured**: falls back to a pure SP-API keyword/brandNames search across 4 phases (A: keyword search per term, strict brand-field matching; B: brandNames-only scan, exhausted to completion via `nextToken`, not capped by `pages_per_brand`; C: a variant scan on brand names seen in Phase B that fuzzy-match an original term; D: a category-partitioned re-scan using classification IDs seen on already-found items, to recover the depth-capped tail of a single keyword query's recall ceiling). SP-API's own search is inherently recall-bound — Phase D cannot surface an ASIN that never matches the brand keyword at all; only a by-ASIN fetch or Keepa gives genuinely complete recall.
- Post-filter (SP-API path): `rapidfuzz.fuzz.token_set_ratio(amazon_brand, search_brand) >= 70`. `_brand_matches(..., strict=True)` in Phase A additionally hard-rejects any candidate whose Amazon brand field is populated and doesn't match (even via title-fallback) — closes a real false-positive class (a keyword coincidentally appearing in an unrelated product's title, e.g. "Ringers" matching "Dead Ringers [DVD]"); non-Phase-A callers keep the looser (non-strict) title-fallback behavior.
- Control: `_BRAND_RUN_CONTROL` dict (pause/stop/resume), same pattern as `services/analytics/runner.py`.
- AI Fill: uses `claude-haiku-4-5-20251001` (Anthropic) or `gpt-4o-mini` (fallback) per item; progress tracked via `ai_fill_done/total` on `brand_analytics_runs`; column-selectable (MPN/UPC/EAN/GTIN, not always all four) via `_clean_ai_fill_fields`; item selection is field-based (`col IS NULL AND ai_col IS NULL`) so re-running for a different column re-processes the same items without needing the item-level done/not-done flag.
- **Global ASIN identifier overrides**: `_upsert_item` reads `asin_identifier_overrides` before the DB write and applies any stored corrections (mpn/upc/ean/gtin). User-corrected values always win over SP-API data, for every future run touching that ASIN.
- **Pack/UOM extraction**: `_extract_pack_qty` (item_package_quantity / number_of_items / title regex) and `_extract_uom_qty` (unit_count / unit_count_type / title regex) populate `pack_qty`/`uom_qty` columns.
- **Unlimited pages**: `pages_per_brand = 0` means no page cap; progress bar shows pulse animation instead of fraction.
- Reuses `normalize_amazon_item()` from `services/analytics/runner.py` — same SP-API normalization as Offer Analytics (see `docs/features/offer_analytics.md`).
