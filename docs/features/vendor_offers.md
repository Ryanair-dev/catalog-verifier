# Vendor Offers / Price Desk

## What this does

A buy-side cross-vendor price comparison tool ("Price Desk") — ingests multiple wholesale vendors' offer catalogs (by file upload or a live Azure DB sync for 5 known vendors), lets a user pair UPCs to ASINs, and produces a formatted Excel export (confusingly also called "Offer Analytics export" in the UI — NOT the same feature as the Analytics-tab "Offer Analysis"/Offer Analytics covered in `docs/features/offer_analytics.md`) combining the cheapest vendor cost with live Keepa/SP-API pricing, fees, eligibility, and ROI.

## Architecture

- **Schema** (`services/vendor_offers.py`, tables namespaced `vo_*`): `vo_vendors`, `vo_products`, `vo_asin_listings` (UPC↔ASIN assignment, `source='manual'`), `vo_vendor_offers` (per-vendor per-UPC offer: cost, available qty, last_seen). `norm_upc`/`offer_key`/a date-guarded `UPSERT_SQL`/`dedupe_offers` form the core merge logic — reused by both the file-upload path (`ingest_vendor_file` → `merge_batches`) and the DB-sync path (`services/vendor_offers_db_sync.py`).
- **File-upload loaders**: `load_quality_king`/`load_cencora`/`load_diamond`/`load_bilo` parse vendor-specific file formats (each with its own quirks: BILO needs xlrd, Diamond is cp1252 + has a 14-vs-13-field quirk, Quality King replays a 7-snapshot stack oldest-first, Cencora is EA-only). All 4 validate UPC shape via `is_valid_upc_a()`/`_upc_a_check_digit` (real UPC-A checksum, not just "12 digits") before accepting a value — a vendor's internal/warehouse code that happens to be all-digits is rejected with a visible skip reason instead of silently creating a phantom product.
- **DB sync** (`services/vendor_offers_db_sync.py`) — for 5 known vendors (Quality King, Cencora, Diamond Wholesale, BILO, Victory Wholesale Grocers), pulls directly from Azure SQL's `fbidb` database (`dbo.vendor_accounts`/`vendor_account_product_listings`/`packaged_products`/`products`) instead of a manual file upload — see `docs/infra/azure_sql.md` for the general Azure connection (NOTE: `vendor_offers_db_sync.py` connects to a DIFFERENT Azure database, `fbidb`, not the `analytics` schema `azure_sql.py` itself targets for the SellerCloud catalog mirror — same server, different schema). `AZURE_VENDOR_ACCOUNT_ID` maps internal vendor names to `dbo.vendor_accounts.id`. Victory Wholesale Grocers has no file-upload parser, so DB sync is the only way to get its offers onto the desk. Runs hourly (`start_scheduler`/`stop_scheduler`, daemon thread, fires immediately on startup then every `INTERVAL_SECONDS=3600`), wired into `main.py`'s lifespan. `clear_stale_available_qty(days=6)` runs in the same hourly cycle, clearing `avail_qty` to NULL (not 0) for any offer whose `last_seen` is >6 days stale, regardless of source.
- **Pairing**: `vo.assign_asin(upc, asin, pack)` / `vo.assign_bulk(...)` (manual, paste-based) and `vo.unassign_asin(asin)` (deletes the `vo_asin_listings` row + mirrors the removal into the Pair Library via `database.delete_library_pair` — see `docs/features/pair_manager.md`). Every manual assignment also mirrors into the shared Pair Library (`database.upsert_library_pair`), growing the curated cross-feature ASIN set.
- **Export** (`services/vendor_offers_template_export.py`, built from `assets/offer_analytics_template.xlsx`) — `build_template_xlsx(upcs=None, focus_vendor=None, apply_filters=False, only_available=False, live=True, populate_keepa=True)`: for each UPC, picks the cheapest (or focus-vendor) offer, enriches with live Keepa data (`services/keepa.py fetch_products`, Buy Box/fees/rank/BB-share/brand/category) and live SP-API (`enrich_asins` — eligibility via `getListingsRestrictions`, storage fee via `getCatalogItem` dimensions, optional generic-ASIN check), computes Net Profit/Margin/ROI/tiered Referral Fee, and writes a 45-column formatted sheet (duplicate-highlight conditional formatting on UPC/ASIN, red-flag CF on Net Margin/ROI/Rank, a yellow "fill this in yourself" FBA column, hyperlinked ASIN links). `_fba_total_by_asin`/`get_units_30d()` (SP-API Reports API, `services/spapi/reports.py`) supply FBA inventory total and 30-day unit sales. This same module's `enrich_asins`/`_fba_total_by_asin` are reused verbatim by PO Analytics (`docs/features/po_analytics.md`) and by `services/analytics/po_analytics.py`. Runs as a background job with progress/ETA/Cancel (poll pattern, see `docs/infra/job_persistence.md`).
- **UI**: `static/price_desk.html`, served inside a same-origin iframe (`#vendor-offers-frame`) embedded in `#view-vendor-offers` (`static/index.html`) — a virtualized ledger table with filter chips (Contested/Stale/Has-ASIN), a price-spread ladder, an item-detail drawer, and an Import modal (file upload + "Sync from Database" + "Sync from Pair Library"). The export's start/poll/download orchestration lives in the TOP-LEVEL `static/app.js` (not inside the iframe) since a hidden iframe's JS timers get throttled/frozen by the browser — `price_desk.html` detects embedding and delegates to `window.parent._voStartExport`/`_voCancelExport`/`_voIsExportRunning` when run inside the SPA, falling back to its own self-contained logic when opened standalone.

**2026-10-20 — Fixed: clicking "Cancel" on a running export didn't actually stop it:**
- User: "for some reason when i click on cancel in the vendor offer analytics it doesnt stop :(" — investigated with a dedicated read-only fork first (see this entry's "Verified" line for what it found) rather than guessing.
- **Root cause, confirmed by reading the code, not assumed**: the cancel flag itself WAS being checked correctly end-to-end (frontend → `/api/vendor-offers/analytics-export/jobs/{id}/cancel` → `job["cancel"]=True` on the live job dict → `should_cancel` threaded into `build_template_xlsx`/`enrich_asins`) — but only BETWEEN completed work items, never DURING one. Three separate low-level retry/backoff loops had zero cancellation awareness: `services/spapi/catalog.py`'s `CatalogAPI._get` (getCatalogItem/getListingsRestrictions, up to 5 attempts × up to 30s backoff on a 429/5xx/network error — this app's own getCatalogItem 429s, reported and partially fixed earlier this session, made this the most likely trigger), `services/restrictions.py`'s own separate copy of the same retry loop, and `services/keepa.py`'s `_wait_tokens` (up to 90 iterations of multi-second polling waits) + `_call_product`'s own retry backoff. With up to 5 ASINs in flight at once in `enrich_asins`'s `ThreadPoolExecutor`, if even ONE worker was stuck in one of these loops, `with ThreadPoolExecutor(...) as ex:`'s implicit `ex.shutdown(wait=True)` on exit meant the WHOLE export (and the Cancel button) had to wait for that worker to finish naturally — up to ~2.5 minutes for the SP-API side, potentially longer for Keepa's token-wait loop.
- **New shared `services/cancellation.py`**: `JobCancelled` exception + `cancellable_sleep(seconds, should_cancel)` (sleeps in ≤0.5s increments, raising immediately the moment `should_cancel()` flips true, instead of blocking for the whole wait). Wired into all three retry loops above (`services/spapi/catalog.py` keeps a `SPAPICancelled = JobCancelled` back-compat alias, since that's where this was first built before being generalised for Keepa too). `CatalogAPI.get_by_asin`/`_get` and `RestrictionsAPI.get_restrictions`/`_get` now accept an optional `should_cancel` param; `services/keepa.py`'s `_wait_tokens`/`_call_product`/`fetch_products` do too.
- **The tricky part wasn't the sleep, it was not re-swallowing the exception**: `enrich_asins()`'s `one()` closure already had broad `except Exception` blocks around both the eligibility and catalog calls (to turn a genuine per-ASIN failure into a blank cell, not kill the whole run) — those would have silently swallowed a `JobCancelled` too and treated a user's cancel click as "this one ASIN failed, keep going." Fixed by adding an explicit `except JobCancelled: raise` BEFORE each broad except, so cancellation propagates out of the worker, is caught where `f.result()` is called in the main collection loop, and converted into the existing `ExportCancelled` the router already handles. Same fix applied to `services/keepa.py fetch_products`'s per-batch `except Exception` — it used to silently `break` on cancel (meaning a Keepa-phase cancel only worked because the sibling eligibility thread usually also noticed independently); it now raises `JobCancelled` properly, converted to `ExportCancelled` where `build_template_xlsx`'s `_run_keepa` thread catches it.
- **Not a regression from this session's `lease_catalog_api` store-splitting work** (previous entry below) — confirmed by the investigating fork: that change only affects which store's `CatalogAPI` instance is used, not the retry loop or executor structure.
- **Verified**: a scripted test with a mocked `requests.get` returning 429 confirmed `CatalogAPI.get_by_asin` now bails out in ~0.5s during a simulated 429 storm (old behavior: up to ~2.5 min). A full `enrich_asins()` integration test (mocked eligibility as always-CAN_SELL, catalog as a permanent 429) confirmed the whole function now raises `ExportCancelled` in ~1.3s after a simulated cancel-click, instead of hanging. A separate test confirmed `services/keepa.py fetch_products` raises `JobCancelled` within ~0.4s out of a simulated exhausted-token-bucket wait. Full app re-imports cleanly (FastAPI TestClient) in both the worktree and the mirrored live checkout.
- **Restart needed**: yes — background-thread Python code changed, not just static files. Left for the user's own timing since a real Vendor Offers export was running at the time this fix was written; mirrored to the live checkout and independently verified importable there without touching the live running process.
