# Pair Manager / Pair Library

## What this does

A manually-confirmed identifier→ASIN library (`pair_library`/`pair_library_ids`) that's distinct from — and takes precedence over — the older `blacklisted_pairs`/`verified_items` tables used by the Verify and Offer Analysis flows (see `docs/infra/database.md`'s "Pair manager integration" section for that older mechanism). Supports spreadsheet import/export, search, and feeds a weekly catalog health-check job (Eligibility + DOG) over the whole library.

## Architecture

- **Schema**: `pair_library(asin PK, brand, manufacturer, amz_pack, created_at, updated_at)` + `pair_library_ids(asin, id_type, identifier, is_primary, added_at, PK(asin, id_type, identifier))` + indexes. Model (post 2026-06-11 remodel): **one UPC may map to MANY ASINs** (many real Amazon listings of the same physical product), and an ASIN keeps its own identifiers (primary + accumulating aliases). Import is the ground-truth write path; spreadsheet-imported pairs always beat system-saved pairs (approve/reject UI clicks, export round-trips) at READ time — `database.load_verified_set()`/`load_blacklist_set()` both exclude a system-saved entry that contradicts an imported Pair Library pair, enforced without touching any write path (re-importing is the way to change/kill a library pair).
- **DB helpers** (`services/database.py`): `upsert_library_pair(asin, ids, brand, manufacturer, amz_pack)` (single locked transaction; mirrors every upc/ean into `verified_items` across all equivalent barcode forms via `_upc_mirror_forms`, deletes conflicting verified rows, clears exact blacklist entries), `delete_library_pair(asin, id_type='', identifier='')` (drop a whole ASIN or one identifier; reverses the `verified_items` mirror; removes the `pair_library` row when no identifiers remain), `pair_library_stats()`, `pair_library_rows(brand="")`, `load_pair_library_map()`, `search_pair_library(q)`.
- **Endpoints** (`routers/pairs.py`): `GET /api/pairs/library/stats`, `GET /api/pairs/library/template?kind=import|lookup`, `POST /api/pairs/library/import` (fixed template ASIN|UPC|EAN|MPN/Item ID|Brand|Manufacturer, case-insensitive header synonyms, multi-value cells, scientific-notation repair, barcode length validation), `GET /api/pairs/library/export?brand=`, `POST /api/pairs/library/lookup-export` (upload UPC/EAN/MPN rows → Matched+Not Found sheets; a complete manual pair not yet in the library is saved as a side effect), `POST /api/pairs/library/search`, `POST /api/pairs/library/delete` (`{asin, id_type?, identifier?}`).
- **UI**: the Pair Manager page has a "Pair Library" card (stats + Import/Export-by-brand/Lookup&Export panels) alongside the pre-existing blacklist search; each library search result row has a ✕ Remove button.
- **Weekly catalog health-check job** (`services/health_check.py`, `routers/health_check.py`) — runs Eligibility (`getListingsRestrictions`) + DOG/dims (`getCatalogItem`, folded into the SAME call since one catalog GET already returns DOG-via-404, brand/manufacturer, AND package dimensions→storage fee) over every ASIN in the Pair Library. Tables: `health_check_runs` (summary) + `health_check_results` (per-ASIN: dog, eligibility, reasons, brand, manufacturer, storage_fee, storage_fee_peak, detail). Backfills accurate brand/manufacturer into `pair_library` from Amazon's own catalog summaries. Scheduled Friday 19:00 `America/New_York` via an in-process daemon-thread scheduler (`start_scheduler`/`stop_scheduler`), only while the app process is running.
- **Price Desk / Vendor Offers imports mirror into the Pair Library** (`services/vendor_offers.py _mirror_pairs_to_library()`) — every manual ASIN assignment on the Price Desk also calls `database.upsert_library_pair`, growing the curated cross-feature ASIN set and giving the UPC↔ASIN sync real barcodes to match against. See `docs/features/vendor_offers.md`.

**Changes this session (2026-10-15b) — Fixed noisy "stop_ev" log lines mistaken for an error; fixed Pair Library import timing out (HTTP 524) on a big file:**
- User reported two things: (1) `"[ai_check] pipeline got stop_ev=<threading.Event at 0x...: unset> for run 149 (id=...)"` appearing in the logs, read as an error; (2) **HTTP 524** when importing `pair_import_template (2) (1)` in the Pair Manager.
- **(1) Not actually a bug — leftover debug logging, now removed** (`services/analytics/ai_check.py`, part of Offer Analysis — see `docs/features/offer_analytics.md`). Traced `_pipeline()`/`stop_ai_check()`: `start_ai_check()` ALWAYS populates `_STOP_EVENTS[run_id]` before launching the AI-check thread (clears a reused Event, or creates a new one), so the "unset" event the user saw is proof everything was working correctly (unset = not stopped) — the line was an always-fires `log.warning` left in from a past debugging session, printed on **every single AI check run**, which is exactly why it read as alarming. Removed the two unconditional warnings in `_pipeline()` (kept the genuine "no stop event found" fallback case, since THAT would be a real bug if it ever happened — downgraded to `log.error` with a clearer message, since it should never fire under normal operation). Also quieted `stop_ai_check()`'s two debug lines (fired on every Stop click) down to one `log.info`.
- **(2) Real bug, root cause confirmed — this is the Pair Library part of the session.** HTTP 524 is specifically "origin didn't respond before the [reverse proxy's] timeout" (Cloudflare's default is 100s) — not something a local FastAPI app can produce on its own, so something fronting this app (a tunnel/proxy) is timing out the connection while the import is still genuinely running. Root cause: `database.upsert_library_pair()` (called once per spreadsheet row by `routers/pairs.py`'s `/pairs/library/import`) opened a **brand-new SQLite connection** (5 `PRAGMA` statements each) **and re-acquired the global write lock, PER ROW** — and within one row, every UPC/EAN identifier fans out into up to ~4 more INSERT+DELETE pairs (one per barcode form, for the `verified_items` mirror + blacklist-clear). A few hundred/thousand-row import (the file name "pair_import_template (2) (1)" implies a real multi-download, likely a real-sized file) easily adds up to well over 100 seconds of pure per-row SQLite overhead even though `asyncio.to_thread` was already keeping the event loop itself unblocked — the SINGLE request still had to wait for all of it before responding.
- **Fix, two parts:**
  1. **`services/database.py`**: `upsert_library_pair`'s body was extracted into a new connection-scoped `_upsert_library_pair_conn(conn, ...)` (same logic, callable against an already-open connection); the public `upsert_library_pair()` is now a thin `with _LOCK, _connect(): return _upsert_library_pair_conn(...)` wrapper (unchanged behavior for every existing caller, e.g. `services/vendor_offers.py`'s mirror-to-library call). New **`upsert_library_pairs_bulk(rows, on_progress=None)`** opens **ONE** connection + **ONE** `_LOCK` acquisition for the WHOLE import and loops `_upsert_library_pair_conn` internally — eliminating the fresh-connection-per-row cost entirely.
  2. **`routers/pairs.py`**: `POST /pairs/library/import` still validates the file (ASIN/identifier columns present) synchronously for an immediate 400 on a wrong template, but the actual import now runs as a **background job** (same pattern as every other slow pipeline in this app — Offer/PO Analytics export, Eligibility/Storage/Generic checks): returns `{job_id}` right away, a daemon thread does the real work via `upsert_library_pairs_bulk`, and a new `GET /pairs/library/import/jobs/{job_id}` is polled for progress/result. This makes the HTTP response itself effectively instant, so no proxy/tunnel timeout can ever fire regardless of how big the file is. **`static/app.js`**'s import handler switched from a single `await api(...)` to a poll loop (shows "Importing… N/Total" live), same toast/result-line behavior as before once the job completes. Deliberately **not** wired into `services/job_persistence.py` (the restart-survival system — see `docs/infra/job_persistence.md`) — a Pair Library import is a one-off action a user watches to completion in the same sitting, unlike a multi-hour export that might span a deploy restart; wiring it in would also mean persisting raw uploaded file bytes as a job param, which isn't worth the complexity here.
- **Verified end-to-end via the real HTTP layer (FastAPI TestClient), not just unit calls**: a synthetic 300-row import (`B0TEST0000`..`B0TEST0299`, clearly test-only ASINs) completed in **0.14s** (300 created, 600 identifiers added, 0 skipped) — proving the perf fix; a bad-template file still gets an immediate clean 400 (no job created); a mixed valid/invalid-row file preserved the exact same skip reasons as before ("Invalid ASIN", "No identifier (UPC/EAN/MPN)"). All synthetic rows cleaned up afterward via `delete_library_pair` — confirmed 0 remaining. `app.js` brace balance exact (2660/2660, same pre-existing +4 paren baseline offset). Full app imports cleanly (153 routes) in both the worktree and the live checkout.
- Scope: `services/analytics/ai_check.py`, `services/database.py` (`_upsert_library_pair_conn` extracted, `upsert_library_pairs_bulk` added), `routers/pairs.py` (import endpoint rewritten as a background job + new status endpoint), `static/app.js` (import handler polls). **Needs a backend restart** (3 Python files changed) + browser hard-refresh.
