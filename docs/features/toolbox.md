# Toolbox (Eligibility / Storage / Generic Check / MPN Check / Quick Search / Check Brand)

## What this does

A slide-in sidebar panel (`#tools-panel`) holding a set of smaller, ASIN/brand/MPN-oriented utilities that don't warrant their own full-page view: bulk ASIN eligibility + FBA storage-fee + generic-ASIN checks, a brand-wide gating check ("Check Brand"), an MPN→qty/case lookup, and (separately, in the Analytics area) a transient single-item Quick Search. Organized as sub-tabs: **ASIN Check**, **Brand Check**, **MPN Check** (PO Analytics was also hosted here 2026-10-12 through 2026-10-15, then given its own context — see `docs/features/po_analytics.md`).

## Architecture

- **ASIN Check sub-tab**: one ASIN textarea + three checkboxes (Eligibility Check / Storage Fees / Generic Check) + Run + per-job progress bars + a combined "Download CSV" (columns: ASIN, eligibility_status, fee_offpeak_per_unit_mo, fee_peak_q4_per_unit_mo, generic_status — whichever were checked).
  - **Eligibility** (`routers/eligibility.py`, `services/restrictions.py`) — live `getListingsRestrictions` per ASIN, 5 workers, store-selectable (Priority Pharmacy / Turba — see `docs/infra/sp_api.md`). Returns CAN_SELL / NEEDS_APPROVAL / RESTRICTED (with a `dog` sub-flag for a 404'd/deactivated ASIN — RESTRICTED category, not a 4th status). Never cached — eligibility is a live, time-varying snapshot of the seller's current gating.
  - **Storage fees** (`routers/storage_fees.py`, `services/storage_fees.py`) — computed from live SP-API `getCatalogItem` package dimensions. 60-day TTL cache (`storage_fee_cache` table, `data_json` column holds the full per-ASIN result so the Tools lookup and the Offer Analytics export's own enrichment share one cache) — see `docs/infra/database.md`.
  - **Generic Check** (`services/generic_check.py`, `routers/generic_check.py`) — classifies an ASIN as DOG (catalog 404) / GENERIC (Amazon's SB85 Generics Policy, detected via a `putListingsItem` `VALIDATION_PREVIEW` call that validates without persisting a listing — issue code 5885) / NOT_GENERIC / ERROR. There is no direct "is this ASIN generic" read endpoint — the validation-preview trick is the only reliable signal found.
- **Brand Check sub-tab** — "Check Brand" (`POST /api/eligibility/check-brand`): answers "are we brand-gated for this entire brand" by sampling a handful of the brand's live ASINs (skipping DOG ones) and checking eligibility on each; rolls up to CAN_SELL / NEEDS_APPROVAL / RESTRICTED (uniform) / MIXED / ALL_DOG. Brand's ASIN list comes from a live SP-API `search_by_keywords(keywords=brand, brand_names=[brand])` call (NOT SellerCloud/Azure — a prior version used Azure, abandoned since Amazon eligibility doesn't need our own catalog at all). Adjustable sample size (fixed count or %, capped at `BRAND_CHECK_MAX=300`) and bulk multi-brand upload (one brand per line, 2-concurrent-worker pool against the same single-brand endpoint).
  - **Brand-name resolution** ("spell check"): when a direct brand search returns 0 ASINs (common when the user's brand string is a sub-brand/product-line name, e.g. "ColorStay" vs Amazon's real catalog `brand="REVLON"`), `check_brand()` tries, in order: (1) a free mechanical resolution — keyword-search without the brand filter, tally the ACTUAL `brand` attribute values on the hits, and re-search using whichever resolved name clears both a vote-share gate (`fraction >= 0.5`) and a text-relatedness gate (`_related()`: partial-ratio ≥90 AND length-ratio ≥0.4, closing two distinct false-positive modes found via a 48-brand calibration set); (2) Keepa's `discover_entities()` (exact structured-field search, same two gates); (3) an AI (Claude Sonnet) guess, gated by `_MIN_VERIFIED_TOTAL=5` real Amazon results under the candidate name before being trusted. All three must clear the same relevance bar — a resolved name with no real Amazon presence correctly 404s rather than guessing.
- **MPN Check sub-tab** — paste `MPN<tab/comma> Manufacturer` pairs (or a single manufacturer for all pasted MPNs); looks up each pair's **Qty/Case** (and **EA/Case**, the fully-expanded each-count) from the FDA's AccessGUDID/openFDA device database (`services/mpn_check_gudid.py`), NOT the Ford Medical fbidb database (which was tried first and found unreliable — see Changelog, 2026-09-25). A fast local SQLite mirror (`services/mpn_check_sync.py`, hourly incremental sync) handles the `product_id` cross-check against our own historical data. An optional, strictly separate "Search the web with AI" toggle (`services/mpn_check.py ai_lookup_qty_case`) runs Claude with web search as a fallback for pairs GUDID can't resolve, verifying rather than guessing (returns `qty_case: null` on anything unconfirmed) — this never feeds back into `qty_case`/`qty_case_uom` (only `ea_case`), since a web search can't reliably determine the intermediate sub-case packaging tier the way GUDID's real hierarchy data can.
- **Quick Search** (lives in the Analytics area, not the Toolbox panel, but documented here as a Toolbox-adjacent utility) — `POST /api/analytics/quick-search`: a transient, single-item version of the Offer Analysis 3-tier search pipeline (UPC/ItemID/Title), no DB writes, scored in-memory with the same matcher as a full run. Also surfaces list price + dimensions + storage fee computed from the same already-fetched SP-API attributes, at no extra API cost. See `docs/features/offer_analytics.md` for the shared matcher/search-tier architecture this reuses.

**Changes this session (2026-10-08d) — MPN Check: fixed a real GUDID root-detection bug (was truncating a 60-unit case down to 10); flagged an unresolved real-world discrepancy on the same MPN:**
- User: "mpn 66800834 is 10 eaches in a bx, and 10 bx in a case which means in total the ea case needs to be 100 but it shows only 10." Pulled the exact raw GUDID record for this MPN live to investigate rather than guess.
- **Confirmed a real bug, found exactly why**: the real record has **5 identifiers in two overlapping chains** (GUDID carries duplicate/legacy packaging chains for the same physical case here) — critically, one identifier's `package_type` is literally **`"Carton"`** (an INNER tier: qty 10, pointing straight to Primary) while the true OUTER case tier is a separate identifier (qty 6, wrapping that Carton). `_case_breakdown_from_identifiers`'s old root-finding logic picked whichever identifier's `package_type` string exactly matched a fixed word list (`{CASE,CS,CTN,CARTON,BOX}`) first in the API's (unordered) response array — here that happened to be the INNER Carton tier, not the true outer root, so the walk started one level too deep and silently truncated a real 6×10=**60**-unit case down to just **10**.
- **Fix**: root detection is now STRUCTURAL, not string-matched — a root is a `Package`-type identifier that is **never referenced as any other identifier's `unit_of_use_id`** (nothing nests above it), found by building the set of all referenced child ids first. When multiple structural roots exist (confirmed live: this MPN genuinely has 2, both correctly totaling 60), a root whose own label textually resembles case/carton/box is preferred as a deterministic tie-breaker only — never the sole detection method anymore.
- **Verified live**: `66800834` → `qty_case=6, qty_case_uom="Carton", ea_case=60` (was `10`); re-ran the full regression set (`CURCHSIL0753`→6/None/24, `STL2644`→100/"Each"/100, `1271`/Teleflex collision→all `None`/`matched=False`) — all still pass, confirming the structural-root fix doesn't regress the simpler single-chain cases.
- **Important, NOT resolved**: the corrected number (60) still does not match what the user described (10 each/box × 10 box/case = 100). This is now a genuine **data discrepancy between AccessGUDID's own registered packaging hierarchy and the user's real-world knowledge of this product** — GUDID's record for this exact MPN structurally says 6 Cartons/Case × 10 Each/Carton = 60, not 10×10. Possible explanations not yet investigated: GUDID's data for this specific MPN could itself be wrong/outdated (manufacturers do submit incorrect UDI data); the user's own case-count knowledge could reflect a different, visually-similar catalog number or packaging variant; or the manufacturer may have changed the real case pack since GUDID was last updated. Flagged plainly to the user rather than silently forcing the output to match their stated 100 without evidence — that would trade a real bug for a fabricated number.
- Scope: `services/mpn_check_gudid.py` (`_case_breakdown_from_identifiers` root-detection rewritten). **Needs a backend restart.**

**Changes this session (2026-09-04j) — Bulk Check Brand: fixed silently stopping after exactly 2 brands:**
- User: "for some reason it only checks 2 and then cancels." Traced it to a real double-handler bug in `static/app.js`: the Check-Brand button had a PERMANENT `addEventListener("click", _checkBrands)` set up once at page load, but `_checkBrands()` ALSO reassigns `btn.onclick = ...` at runtime (to a Cancel handler while a bulk run is in progress, then back to `_checkBrands` when done) -- `.onclick` assignment does NOT replace a handler added via `addEventListener`; both fire on every click.
- **Mechanism, confirmed by tracing the exact reported symptom (2 = the CONCURRENCY constant):** a second click on the button during a bulk run -- the button now reads "Cancel" -- fires BOTH handlers for that one click. The addEventListener's `_checkBrands` runs first (its synchronous setup resets `_brandCheckState.cancel = false` and launches a fresh pool of 2 concurrent workers, each already past their first `await` before yielding back to the browser), THEN the onclick handler for that same click fires and sets `cancel = true`. The 2 in-flight requests (matching `CONCURRENCY = 2`) still complete and get recorded, but every worker's loop then sees `cancel === true` on its next iteration and stops -- so it always halts at exactly 2, regardless of how many brands were queued.
- **FIX:** removed the `addEventListener` entirely; the button now uses ONLY `.onclick`, set once at setup to `_checkBrands` -- every later reassignment (Cancel handler, then back to `_checkBrands`) now correctly REPLACES the single handler instead of stacking a second one alongside it.
