# Competitor Analysis

## What this does

For one of **our** products — already on Amazon or not yet — find every Amazon listing of the **same item from other brands** and size up that market: how many listings and brands, units sold and revenue per month, price **per unit** (avg / median / units-weighted / lowest / highest), best sales rank, which brands lead, who holds the Buy Box, FBA vs FBM, whether Amazon itself sells it. Close variants (e.g. a 3.5" knife when ours is 3") are listed separately, never mixed into the market totals.

Toolbox → **Competitor Analysis** tab. One product (description, optional our ASIN, optional our price per unit, optional extra search phrases) or a **bulk** spreadsheet (one product per row, max 50; template at `GET /api/competitor-analysis/template`). Result: an xlsx (Summary / Competitors / Brands / Sellers (exact) / Excluded / How to read) plus an on-screen summary per product.

Not the same as Jordan's AmazonAsinResearch1 "competitor analysis" (a category-level revenue-by-brand report with no spec matching, no per-unit price) — that repo was read for reference; only its sales-from-rank power law and variation bonus were ported. See the 2026-11-03 changelog entry.

## Architecture

- **`services/competitor_analysis.py`** — `run(products, on_progress, should_cancel)` → `(xlsx bytes, results)`; per product `analyze_product()`:
  1. **Plan** (`plan_product`, Claude `claude-sonnet-4-6`, tool-use JSON `_PLAN_TOOL`): product type, one-line spec, unit name ("knife"), exact criteria (with tolerances, e.g. 2.75–3.25 in), close criteria, 4–8 SP-API search phrases (no brands, spec spellings 3 inch / 3" / 3-inch), 2–5 Keepa title word-sets (first broad, then spec-narrowed). If our ASIN is given its SP-API title is fed in; with no description the title becomes the description.
  2. **Discover**: `_sp_search` — SP-API `searchCatalogItems` per phrase, up to `SP_PAGES`=10 pages ×20, `includedData=summaries,attributes,salesRanks`; keeps title, brand, browse classification and a compact attribute string (`_attr_text`: size, style, blade, item_length, number_of_items, unit_count, item_package_quantity, …). `_keepa_finder` — Keepa Product Finder `{"title": term, "current_SALES_gte": 1, "sort": [["current_SALES","asc"]]}` (title = AND of words; ranked products only, best rank first), `KEEPA_BROAD_CAP`=800 from the first term, `KEEPA_NARROW_CAP`=500 from each narrowed one, total capped at `MAX_CANDIDATES`=2500.
  3. **Titles** for Keepa-only ASINs: `_keepa_titles` — light `/product` with `history=0` and no stats (~1 token/ASIN).
  4. **Classify**: `_classify_batch`, 40 listings/call, 6 workers, `_CLASSIFY_TOOL` → per ASIN `verdict` exact/close/not, `units_in_listing` (2-pack = 2), `spec_seen`, `reason`.
  5. **Enrich** exact + close only (+ our ASIN): `keepa.fetch_products` (2-day `keepa_product_cache`, ~12 tokens/ASIN live) → Buy Box price (current, else 30d/90d avg), monthlySold, rank, reviews, rating, BB seller (name), Amazon BB %, FBA/FBM offer counts, parent ASIN.
  6. **Re-check exact** (`_verify_exact_batch`): a second, stricter pass over exact rows only, now with the price and the median single-unit price — demotes clearly-out-of-spec rows to close (or drops them to Excluded) and fixes implausible pack counts; changes are written to the row's `note` (Competitors → Note column). Prompt explicitly says: judge only against the plan's criteria, tolerance ranges are inclusive, when in doubt keep exact (see changelog for why).
  7. **Units / revenue** (`_apply_units`): per variation family (Keepa `parentAsin`): children with Amazon's own "bought in past month" keep it; their unreported siblings get none ("Variation (sales on sibling)"); a family with nothing reported gets ONE estimate from `fit_units_model` (units ≈ a·rank^b·(reviews+1)^c, OLS in log space on this run's own reported rows, ≥`MIN_FIT_POINTS`=20, rank-only fallback; requires b<0) split across members with +5% per extra member. Revenue = price × units.
  8. **Roll-ups**: `_market` (exact and close separately), `_rollup` by brand and by Buy Box seller; our price per unit (given, else our ASIN's) → "cheaper than X% of exact matches".
  `build_workbook(results)` writes all products into one workbook (a Product column on every sheet); `summary_for_ui` is the small JSON the tab renders.
- **`routers/competitor_analysis.py`** — `POST /start` (JSON), `POST /start-bulk` (multipart; column aliases in `_COLS`: Description/Product/Item/Title, Our ASIN/ASIN, Our Price/Price, Extra Search Terms/Keywords), `GET /template`, `GET /jobs/{id}` (status + `summary` when done), `POST /jobs/{id}/cancel`, `GET /jobs/{id}/download`. Same in-memory job store pattern as Seller Analytics; `job_persistence` type `competitor_analysis` (relaunched fresh after a restart with the same job id), finished files saved via `job_results` (14 days), `list_jobs_for_tasks_panel()` registered in `routers/settings.py`.
- **UI** — `static/index.html` `#tools-tab-competitor`, `static/app.js` `_caStart` / `_caPollNow` / `_caRenderSummary`; the running job id is kept in `localStorage["ca_job"]` so a page reload picks the job back up.

**Cost / time (3-inch paring knife, live 2026-11-03):** ~7.5 min; ~1,390 listings screened (≈510 from SP-API, ≈880 from Keepa); Keepa ≈945 tokens for finder + titles, plus ~12 tokens/ASIN for the ~1,000 exact+close listings on a cold cache (cached for 2 days after); ~35 Claude Sonnet calls for classification + ~5 for the re-check.

**Known limits:** "bought in past month" is Amazon's rounded lower bound (1K+ = 1,000); the rank→units fit is weak on this kind of data (R² ≈ 0.22–0.26 for knives) — the Summary shows R² and the share of units that were estimated; a listing whose title contradicts its price (e.g. "24 Pack" at $10.75) follows the title; listings with no sales rank are not discovered by the Keepa leg (only by SP-API search); SP-API keyword search stops at 10 pages per phrase.

- User decisions (asked): one product **or** bulk per run; exact + close **kept separate**; sources **SP-API + Keepa** (no SerpAPI).
- Live probes before building: SP-API "3 inch paring knife" → numberOfResults 1,247, attributes include `size` ("3\""), `style`, `number_of_items`, browse class "Paring Knives"; Keepa finder `title` filter works and is an AND of words ("paring knife" 9,903 vs "paring knife 3 inch" 572), ~11 tokens/query.
- Live run 1 (3-inch paring knife): worked end to end in 441 s, but three problems found in the output: a $10.75 Dexter "24 Pack" became $0.45/knife (lowest price), a 3.74" knife was called exact, and variation children sharing the parent's sales rank each got their own estimate (44 of 196 estimated exact rows shared a rank) → inflated units. - Live run 2: those were fixed, but the re-check over-corrected — it demoted 3.25" knives "at the upper tolerance limit" (inclusive boundary) and invented a criterion (serrated edge), pushing Victorinox's classic 3.25" knife (the category leader) into close. Prompt changed (inclusive ranges, no new criteria, keep exact when in doubt); re-tested on exactly those 20 disputed rows + 5 controls: 3.25"/2.75" knives back to exact, 3.4"/3.5"/9 cm/3.74" correctly close.
- Also: `services/keepa.py` `_flatten_product` gained a `rating` key (see `docs/infra/keepa.md` 2026-11-03); `routers/settings.py` Tasks Running lists these jobs; CLAUDE.md feature index + file map updated.
